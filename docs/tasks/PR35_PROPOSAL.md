# PR35+ 設計方針提案: `Bond::setup()` のスケーラビリティ改善

本ドキュメントは、`TASK_PR35_bond-setup-scalability.md` の着手に先立ち、Claudeによるレビューおよび方針確認のために作成された設計提案書です。

## 1. 近傍探索アルゴリズムの選定

### 採用方針: 一様な空間セルリスト (`CellList` / Uniform Grid)
- **選定根拠**:
  - タンパク質や生体高分子の原子密度はほぼ一様であり、空間分割木（BVHやOctree）のような木構造の構築・スタック走査のオーバーヘッドを避けられるため、単純かつ高速（$O(N)$）に動作します。
  - 最大カットオフ距離 $R_{\text{cut}} = \max(\text{vdw}_p + \text{vdw}_q) + 0.4 \approx 5.4 \text{ \AA}$ に対し、セル幅 $S = 6.0 \text{ \AA}$ のグリッドに空間を分割します。
  - 各原子は自身が属するセルおよび隣接セル（重複を防ぐため順序付けられた13セル＋同一セル内の $q < p$）のみを走査することで、ペアごとの判定回数を $O(1)$ に抑制します。

## 2. 既存 public フィールド (`distmat` / `bondmat`) の後方互換性方針

### 現状と課題
- `Bond` 構造体は `pub distmat: Option<SymmetricMatrix>` および `pub bondmat: Option<SymmetricMatrix>` を持ち、既存テスト（`test_bond_setup` 等）で直接参照されています。
- 一方、全原子ペアの $O(N^2)$ 行列を無条件に保持すると、10万原子で約40GB、100万原子で約4TBとなり即座にメモリ不足（OOM）でクラッシュします。

### 提案方針: 閾値によるハイブリッド動作
1. **小規模構造 ($N \le 2,000$ 原子、メモリ約16MB以下)**:
   - 既存テストおよびレガシーコードとの完全互換性を維持するため、従来通り `distmat` / `bondmat` を構築して保持します。
2. **大規模構造 ($N > 2,000$ 原子)**:
   - メモリ保護のため `distmat = None` / `bondmat = None` とし、$O(N^2)$ 行列のアロケーションをスキップします。
   - `mol.add_bond()` による結合トポロジーの登録は、セルリストを用いて直接 $O(N)$ 時間・最小限のメモリで実行します。
3. **明示的クエリ**:
   - 必要に応じて、特定のペア間の距離を取得するヘルパー等の追加も可能です。

## 3. 公開する低レベル近傍ペアクエリ API

YUI 側（`core::spatial::AtomBvh` 相当の用途）や今後の他用途（非共有結合探索等）への再利用を考慮し、再利用可能な空間分割構造体・関数を `bond.rs`（または `spatial.rs`）に新設・公開します。

```rust
/// 一様グリッドによる3次元空間分割構造体
pub struct CellList {
    cell_size: f64,
    grid: std::collections::HashMap<(i32, i32, i32), Vec<usize>>,
    positions: Vec<Position>,
}

impl CellList {
    /// 原子座標スライスとセルサイズからセルリストを構築 (O(N))
    pub fn new(positions: &[Position], cell_size: f64) -> Self;

    /// 指定半径内の原子ペア (i, j) [i < j] と距離のリストを列挙
    pub fn query_pairs_within(&self, radius: f64) -> Vec<(usize, usize, f64)>;

    /// コールバックによるイテレーション（大量ペア時のメモリ確保を抑えたい場合）
    pub fn for_each_neighbor_pair<F>(&self, max_radius: f64, mut callback: F)
    where
        F: FnMut(usize, usize, f64);
}
```

## 4. 検証とベンチマーク計画

1. **既存テストの回帰確認**:
   - `test_bond_setup` / `test_bond_setup_empty` がすべてパスすること。
2. **正当性検証テスト**:
   - 中規模構造（数万原子）において、セルリストによる新実装が、旧 $O(N^2)$ の総当たり距離行列実装と「**完全に同一の結合ペア集合**」を検出することを自動テストで検証。
3. **100万原子規模の性能ベンチマーク**:
   - 100万原子規模の合成構造（アミノ酸等の妥当な原子密度の配置）に対して `Bond::setup()` を実行。
   - 実行時間およびメモリ使用量の概算を計測し、`docs/rust-port-handoff.md` に結果を記録。

## レビュー結果(2026-09-19、着手前の方針確認)

全体方針(セルリスト、half-neighbor方式)は`TASK_PR35`の推奨アプローチと一致しており妥当です。実装着手前に、以下4点を解消・明確化してください。

### 要修正・要明確化(実装前に決めること)

1. **セルサイズを固定値にしないこと**: `S = 6.0 Å`が固定定数として提案されていますが、これは「典型的なC/N/O/H中心の$R_{\text{cut}} \approx 5.4$ Å」という一例からの逆算に見えます。VDW半径は元素によって大きく異なり(例: I, Fe等の重元素はより大きい)、実際にPRMTOP/MOL2経由で読み込まれる構造にはどんな元素も含まれ得ます。**セルサイズは実行時に`mol`内の実際の原子集合から`max(vdw_p) * 2 + 0.4`(またはそれ以上の安全マージン)を計算して動的に決定してください。** 固定値のままだと、セルサイズより大きいカットオフを要する原子ペアの結合を、エラーなく静かに見逃す(=検出漏れ)結果になります。これは`Bond::setup()`が現在使っている`self.atoms[p].vdw()?`を先に一括収集すれば実装可能です。
2. **正当性検証テストの規模を分離すること**: DoD項目2の「数万〜十万原子で旧$O(N^2)$実装と完全に同じ結合ペア集合を返すことを検証」を、そのまま通常の`cargo test`(デバッグビルド)内で実行すると、参照実装側の$O(N^2)$計算だけで数万原子規模はかなり重くなります。PR#30で「タイミングベースのテストがCIでフレーキーになり得る」という指摘をした経緯もあるため、**正当性の等価性検証(新実装 vs 旧$O(N^2)$実装の結合ペア集合比較)は数千原子程度の規模に留め**、DoD項目3の「100万原子規模の性能ベンチマーク」(こちらはタイミング計測が主目的)は`#[ignore]`付き、または`--release`前提のベンチマークとして分離することを推奨します。PR#30と同様、性能計測に`assert!`で閾値判定をかけるのではなく計測結果を出力するだけに留めてください。
3. **`distmat`/`bondmat`が`None`になる閾値を公開APIの仕様として明記すること**: $N > 2,000$で`distmat`/`bondmat`が`None`になるのは、まさにこの機能が対象とする大規模構造(数十万〜100万原子)で常に発生する挙動変更です。これらのフィールドに直接依存する既存コード(YUI側含む)への影響があるため、(a) 閾値をマジックナンバーではなく名前付き定数にする、(b) `distmat`/`bondmat`のdocコメントに「$N$が閾値を超える場合は`None`になる。大規模構造での近傍ペア取得には`CellList`(またはボンドリスト経由のAPI)を使うこと」を明記する、の両方を実装に含めてください。
4. **`CellList`の配置先は`spatial.rs`を推奨**: `bond.rs`に置くか`spatial.rs`に置くか未決の点について、YUI側`core::spatial::AtomBvh`相当の汎用近傍探索用途(将来的に水素結合・CH-π等、他のO(n²)探索箇所の置き換えにも使われうる、TASK_PR35のスコープ外注記にある通り)を考えると、`bond.rs`に結合しない`spatial.rs`(新設)に置く方が、将来の再利用時に`bond`モジュールへの不要な依存を作らずに済みます。

### 軽微な指摘(対応推奨だが必須ではない)

5. `for_each_neighbor_pair`のコールバックも、`query_pairs_within`と同じ`i < j`(重複・自己ペアなし)の順序規約を持つことをdocコメントで明記してください。両者で規約が暗黙的に異なると誤用の元になります。

上記1〜4を反映した上で実装に進めてください。実装後、通常通りブランチ・テスト結果をユーザー経由で報告し、レビューを受けてください。
