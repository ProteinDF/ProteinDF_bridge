## 2. 保持対象（教訓・ハマりどころ・設計判断・失敗事例）一覧

以下の項目は、将来の実装や YUI 統合において同じ失敗を繰り返さないために**絶対に削除・圧縮せず保持する**。

### A. データモデル・メモリ管理・所有権
1. **`bonds` フィールドのマージ漏れ（Phase 1 是正事項 5）**:
   - `AtomGroup::merge`/`BitAnd`/`BitOr`/`BitXor` 等で `bonds: Vec<BondRecord>` がマージされずサイレントに消失していた。
   - **教訓**: `AtomGroup` に新フィールドを追加する際は、`Clone` およびすべての集合・マージ演算を洗い出して対応すること（Phase 10 PR#29 `secondary_structure` 追加時にも実際に引用・機能した実例）。
2. **`add_bond`/`get_bond_list` の共通祖先ルーティングと相対パス格納（Phase 2 PR#4〜6）**:
   - ネストした階層構造（model/chain/residue）で異なる枝にまたがる結合（SSBOND等）を扱う際、呼び出し元に絶対パスで格納すると、親グループの再配置時にパスが古いまま取り残される。
   - **設計判断**: 2原子の共通祖先グループ（`get_common_path`）を探し、そこからの相対パスで格納。`get_bond_list()` で絶対パスを復元するルーティングを実装。
3. **0次元行列での panic（Phase 1 是正事項 3, 10）**:
   - `Matrix::new` が `rows>0 && cols>0` を assert していたため、原子数 0 の `AtomGroup` に対する `Bond::setup` でクラッシュしていた。
   - **教訓**: 0次元（空の系）を正常系として許容し、`SymmetricMatrix::eig()` の n=0 分岐の形状整合を保つ。
4. **`AtomGroup::merge` のサブグループ照合ロジック（Phase 1 是正事項 6）**:
   - key 一致のみ見ていたため、本来統合されるべきグループが重複した兄弟グループとして分裂。Python 版の「key 一致 OR `name` 一致」フォールバックを再現。
5. **コレクションの順序決定性（Phase 1 是正事項 9, Phase 7 PR#20, Phase 8 PR#22）**:
   - `HashSet` の利用や、`IndexMap` の挿入順への暗黙的な依存により、残基走査や集合演算の順序が非決定的・実行順依存になっていた。
   - **教訓**: 残基列挙では `sort_nicely` による自然順ソートを明示的に行い、`IndexMap` の挿入順に依存しないこと。
6. **大容量データでのメモリ保護（Phase 10 PR#35）**:
   - 100万原子規模では従来の $O(N^2)$ 密行列（`distmat`/`bondmat`）が約 4 TB を消費しメモリ枯渇を引き起こす。
   - **設計判断**: `MAX_DENSE_MATRIX_ATOMS = 2000` を公開定数とし、2,000原子超では密行列の生成をスキップして `None` を設定。

### B. 幾何計算・アルゴリズム
7. **Python 版 `superposer_quaternion.py` の実バグ発見（Phase 3 PR#11）**:
   - Python 版では `SymmetricMatrix.add()` が下三角に正規化されておらず、`numpy.linalg.eigh` が下三角しか読まないため非対角成分が実質無視されていた（Kabsch法 RMSD≈6e-16 に対し四元数法 RMSD≈0.549 と乖離）。
   - **設計判断**: 実験的モジュールのバグを模倣せず、Rust 側で正しい対称書き込みを優先し Kabsch 法と一致させた（RMSD≈3e-16）。
8. **二面角計算の数値安定性と定義（Phase 7 PR#20）**:
   - IUPAC 標準に従い、数値的に安定な `atan2` 方式を採用。
   - 末端残基（最初の残基の φ、最後の残基の ψ）は定義不能なため `Option<f64>`（`None`）とし、主鎖欠損残基は可視化目的のため安全にスキップする設計。
9. **Kabsch-Sander 水素結合・DSSP の判定バグと修正（Phase 8 PR#22, PR#23）**:
   - 欠損残基フィルタ後の配列インデックスで隣接残基距離判定（`|d-a|<=2`）を行ったため、鎖内に欠損残基が連続すると誤除外されるバグを発見（`orig_idx` ベースに是正）。
   - 逆平行ブリッジの式におけるインデックスずれの発見と手計算による再導出・修正。
   - 8状態 DSSP を可視化リボン用途に合わせて H（ヘリックス統合）/E（ストランド）/-（ループ）の 3 状態に意図的に簡略化した設計判断。
10. **CH-π 相互作用の幾何判定と落とし穴（Phase 9 PR#25）**:
    - 環法線ベクトルは最小二乗平面フィット（SVD）で求めるが、法線の向き（符号）は数学的に不定であるため、角度判定では必ず内積の絶対値（`|dot|`）を取る必要がある。
    - `is_carbon_atom` が原子名 "C" 始まりだけで判定していたため、塩化物イオン "CL" を誤検出していたバグ（`atomic_number() == 6` のみに是正）。
11. **セルリスト近傍探索のスケーラビリティ（Phase 10 PR#35）**:
    - 結合探索を動的セルサイズ（`(2 * max_vdw + 0.4).max(3.0)`）のセルリスト（half-neighborhood 13方向探索）で $O(N)$ 化。
    - コールバックAPIでのインデックス順序規約 `i < j` の保証。
    - 100万原子で 3.39 秒（リリースビルド）、結合 1,273 万件検出の実測値。

### C. フォーマット・パーサ・I/O
12. **mmCIF の実態とカラムマッピングの落とし穴（Phase 4 PR#12, PR#13）**:
    - Python 版 `SimpleMmcif` は CCD 形式（単一化学成分）のみで、全体構造（`_atom_site`）に未対応だった。
    - `label_asym_id`/`label_seq_id` をチェイン/残基番号に使うと、水分子等の残基がすべて 1 つに潰れる実バグが発生するため、PDB互換著者番号である `auth_asym_id`/`auth_seq_id` を採用。
13. **文字列処理・パーサのエラーハンドリング（Phase 1 是正事項 4, Phase 2 PR#4）**:
    - `unwrap_or(0.0)` や `unwrap_or(0)` によるサイレントなエラー握りつぶしの危険性（VDW未知元素で結合判定スキップ、GRO のオーバーフロー `*****` が原子0番として誤混入）。
    - GRO 固定長パースでのバイト単位スライス（`line[0..5]`）が非ASCII文字で panic する問題（`.chars()` ベースの採用）。
    - `xyz.rs` で宣言原子数より実データ行数が少ない場合に黙って `Ok(())` で抜けていた問題。
14. **`.brd` (MessagePack) の互換性と YUI ヘッダー（Phase 6 PR#17, PR#18）**:
    - 既存 Python 版 `.brd` は YUI ヘッダーを持たないプレーン MessagePack であり、`modeling.py` がコンストラクタで無条件にロードしていた。
    - 既存プレーン形式と YUI 互換ヘッダー（Magic+Version+zstd）形式を別 API として両立させた設計。
    - `neutralize.py` の `_exempt_list` が Python 版で実質機能していなかったため、そのまま再現した経緯。
15. **ファイル由来結合とヒューリスティック結合の優先順位（Phase 10 PR#31〜34）**:
    - MOL2, PRMTOP, PDB CONECT 由来の正確な明示結合が存在する場合はそれを優先し、`Bond::setup()`（ヒューリスティック）による上書き・二重生成を行わないポリシー（`RUST_PORT_SPEC.md` §3.8）。
16. **テストフィクスチャのパス解決（Phase 2）**:
    - テスト内でのフィクスチャ参照はカレントディレクトリ（CWD）依存を避け、`env!("CARGO_MANIFEST_DIR")` 基点の絶対パスを使う（過去に CWD 依存テストが壊れた事例）。

### D. 運用ルール・依存ライブラリ選定・アーキテクチャ構成

    - `rust-port` 統合ブランチ時代から `2026.9.0` リリース後の GitFlow 運用（`develop` 起点・合流）への変遷。

### E. 検証方法論（Methodology）
21. **「新規機能・テスト不足モジュールは独立検証で担保する」という横断的検証方針**:
    - 既存Python版にテストが存在しない（`modeling.py`/`neutralize.py`の除外）、または合成1件しかなく受け入れ基準にならない（`mmcif.py`の除外）モジュールは、拙速な1:1移植を行わず、検証基準とテストフィクスチャを整備するまで独立フェーズとして分離・再設計した。
    - Python版に対応実装がない新規機能（Ramachandran、DSSP二次構造、側鎖H-bond、CH-π、MOL2/PRMTOP/PDB CONECT結合I/O）では、「Python版との1:1比較」という受け入れ基準が使えないため、**「(1) 文献値・一次アルゴリズムに基づく独立手計算基準値（実データ相互照合）」＋「(2) 境界値・幾何学的サニティを保証する合成データテスト」** の2段階検証を徹底。これによりPython版の実バグ（四元数法の対称行列非対角成分無視など）に引きずられず、正しい挙動を担保した。

### 追加してほしい教訓1: 「新規機能は独立検証で担保する」という検証方針そのもの

個々のバグ事例より一段上の「方法論」として、以下のパターンがPhase 3・4・7・8・9・10で繰り返し採用されている:
- Phase 3: `modeling.py`/`neutralize.py`をテストが薄すぎる(専用テストファイルなし)という理由でPhaseから除外(37〜204行目)。
- Phase 4: mmCIFを「既存テストが合成データ1件のみで受け入れ基準にならない」という理由で除外・再設計(120〜122行目)。
- Phase 7〜10: Python版に対応実装が無い新規機能(Ramachandran、DSSP、側鎖H-bond、CH-π、MOL2/PRMTOP/PDB CONECT読み込み)は「Python版との1:1比較」という通常の受け入れ基準が使えないため、**独立計算した基準値・実データ相互照合・境界値の合成データテストで正当性を担保する**、という2段階検証方式を毎回採用(464行目、536行目、731行目等)。
